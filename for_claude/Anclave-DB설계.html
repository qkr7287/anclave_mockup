Anclave — DB 설계

목업을 실제 서비스처럼(사람 간 공유 · 시간 누적) 동작시키기 위한 데이터베이스 설계. DB는 PostgreSQL(외부 플랫폼 X), 데이터 접근은 얇은 Hono backend(REST) — 방식 A. 지금은 로컬 Docker로 DB만 띄우고, 나중에 frontend+backend 이미지로 63번에 올림. 근거 모델 = app/src/data/types.ts(§13 스키마) · 시드 = app/src/data/seed.json.

0개요 & 전략

왜 DB인가

요구사항: A가 오늘 신청 → B가 내일 보고 → A가 승인하면 B에게 보이고 → 대시보드는 어제+오늘 누적. 이건 "시간의 함수"가 아니라 어딘가 저장된 사실이라 localStorage·시간생성기로는 불가능 → 공유 DB 필요.

하이브리드 원칙 (핵심)

거의 전부 DB. 사람 간 공유·시간 누적되는 사실은 물론, 사용률·온도·전력 같은 텔레메트리도 DB 시계열로 저장(아래 ★ 텔레메트리 적재). 초기 설계의 클라이언트 f(now) 생성은 폐기 — 브라우저마다 값이 달라 비현실적이라(사용자 지적 반영).

구분대상이유
DB 저장 신청·승인·서비스·마켓 게시·API키·할당(슬라이스 소유)·모델·이벤트로그·감사로그·게시판·알림 시간순 누적 + 사람 간 공유 = "어제 신청 + 오늘 추가"가 진짜로 됨
텔레메트리(DB 시계열) GPU 작업률·VRAM·온도·전력, 서버 CPU/MEM·네트워크, 슬라이스 usage, 서비스 토큰 3단 tier(현재값 5초 / 원본 1분·48h / 1시간평균 30일)로 저장 → 브라우저 공통·시간 누적. ★ 섹션 참고
seed.json의 운명: 버리지 않고 "DB 최초 1회 적재용 시드"로 강등. seeding 후엔 DB가 정본. data/*.ts 로더는 점진적으로 Hono API 훅으로 교체.

호스팅: Plain Postgres + 얇은 Hono backend (방식 A · 외부 플랫폼 X)

브라우저는 Postgres에 직접 연결 못 한다(드라이버·보안·CORS). 그래서 DB 앞에 얇은 backend(Hono)를 직접 둔다 — SQL을 감싼 REST + 적재 워커. Supabase 같은 외부 스택 미사용.

[Vite 프론트] --fetch(REST)--> [Hono backend] --SQL--> [PostgreSQL (Docker)] │ (데이터 · 정본) ├─ REST API (화면별 query / mutation) └─ 적재 워커 (5초 현재값 · 1분 원본 · 1시간 롤업 · 이벤트 룰) [지금] 셋 다 내 PC 로컬 (DB만 Docker) [나중] frontend+backend 이미지 → 63번(192.168.0.63)

→ 100% 자체 코드·인프라. 컨테이너 가벼움(postgres 1개). 실시간 갱신은 5초 폴링으로 충분(목업).

1어디에 무엇을 — 필드 단위 분류

types.ts의 각 인터페이스에서 엔티티 컬럼(고정 속성·관계)과 텔레메트리(시간에 따라 변하는 측정값)를 가른 표. 둘 다 DB지만 저장 방식이 다르다 — 컬럼은 엔티티 테이블, 텔레메트리는 시계열 테이블(★ 섹션).

인터페이스엔티티 컬럼 (엔티티 테이블)텔레메트리 (시계열 테이블)
Gpuid, server_id, name, model, arch, vram_gb, mig_capable, serial, health, alloc_mode, assigned_user_id, assigned_service_id, interconnect, xidsm_util, vram_util, temp, power
GpuServerid, name, rack, host, network, note, health, hosted_*cpu_util, mem_util, net_in, net_out, temp
MigSliceid, gpu_id, profile, units, gb, owner_user_id, model_id, container_id, health, request_idusage, vram_util (서비스의 할당공간 사용률)
Serviceid, name, model_id, owner_user_id, … (스키마 §4)tokens, calls (앱 지표만 — 자원은 할당 슬라이스에서 파생)
그 외 전부스칼라·관계 필드는 전부 엔티티 컬럼 (텔레메트리 없음)
health(상태)는 현재 사실이라 엔티티 컬럼. 단 텔레메트리 적재 워커가 임계치를 넘으면 health·event를 자동 갱신(★ 이벤트 룰). 서비스의 vram·온도·전력 등은 별도 저장 없이 할당받은 슬라이스→GPU→서버를 타고 파생(한 GPU에 서비스 여럿이어도 슬라이스 단위로 구분).

★텔레메트리 적재 아키텍처

사용률·온도·전력·토큰처럼 시간에 따라 변하는 측정값을 DB에 저장해, 어느 브라우저에서 봐도 같고 시간 누적되게. 정책 5가지 — 측정 대상 · 3단 tier · 정상범위 생성 · 이벤트 룰 · 헬스 대시보드.

① 측정 대상 4종 (다대다 대응)

한 GPU에 서비스 여러 개가 올라가도 각자 값을 갖도록, 서비스는 토큰만 직접 측정하고 자원(vram·온도 등)은 할당받은 슬라이스→GPU→서버를 타고 파생.

대상직접 쌓는 지표비고
servercpu_util · mem_util · net_in · net_out · temp서비스 CPU/메모리 = 내 서버 값
gpu작업률(sm) · vram · 온도 · 전력물리값. 서비스 온도/전력 = 내 GPU 값
sliceusage · vram할당공간 = 격리 단위 → 서비스 vram/사용률은 여기서
servicetokens · calls앱 지표만 직접

② 3단 tier — 부하 없이 평균·200점·7일

tier간격보존쓰는 뷰
latest5초 덮어쓰기1행/시리즈KPI 숫자·게이지·평균
raw1분48시간3h·6h·24h 그래프(100~200점)
hourly1시간 평균30일7일·30일 그래프

읽을 때 범위 보고 tier 자동 선택 → 어떤 화면이든 수백 행만 읽음 → 로드 일정. 7일은 hourly(168행)에서 읽어 raw 안 건드림.

-- long format: 지표 추가가 행만 추가(스키마 불변), 다대다 자유
create table telemetry_raw (
  ts      timestamptz not null,
  kind    text not null,   -- server | gpu | slice | service
  id      text not null,   -- 대상 엔티티 id
  metric  text not null,   -- cpu_util | sm_util | vram | temp | power | tokens ...
  value   real not null
);
create index on telemetry_raw (kind, id, metric, ts desc);  -- 시리즈+범위 즉시 점프(풀스캔 X) → 테이블 커도 빠름
-- telemetry_hourly = 동일 구조(value=시간평균) · telemetry_latest = ts 없이 1행 upsert

③ 정상범위 생성 — "예쁜" 차트

더미를 지표별 현실 정상범위 안에서 자연스럽게 출렁이게(일주기 + 노이즈). 상태별로 다르게 — 정상=정상범위 / 유휴=거의 0 / XID 장애=비정상·끊김.

지표정상범위패턴
GPU 작업률20~85%낮↑/밤↓ + 노이즈
GPU 온도38~74°C작업률 따라감
GPU 전력TDP의 30~90%작업률 비례
서버 CPU / RAM15~70% / 30~75%완만
서비스 토큰트래픽 곡선업무시간 ↑

④ 이벤트 자동 발생 — backend 워커 룰 (방식 B 확정)

1분 적재 때 워커가 임계 룰을 평가 → 넘으면 event_logs에 INSERT(DB 트리거 대신 워커 — 룰 수정 쉽고 부하 적음). 같은 대상에 open 이벤트 있으면 중복 안 만듦(디바운스).

룰이벤트
GPU 온도 > 85°Cwarn · 온도 경고
전력 > TDP 95%warn · 전력 경고
할당됐는데 작업률 0 지속info · 유휴 경고
XID 발생critical · 위험

→ 4.2 알람·4.21 타임라인이 텔레메트리에서 자동으로 생김(진짜 관제처럼).

⑤ 적재 헬스 대시보드

backend가 잘 넣고 있나 확인하는 개발/운영용 페이지(/admin/telemetry-health) + /stats 엔드포인트.

워커 상태 (running / 마지막 실행) tier별 행 수 (latest/raw/hourly) + 용량 최근 1분 INSERT 수 (정상 ~120) 시리즈별 최신값 샘플 보존 청소 동작 (48h / 30일) 이벤트 트리거 발생 수

용량 (서버8·GPU9·슬라이스~15·서비스7 = ~120 시리즈)

latest 120 시리즈 × 1 = 120 행 raw 120 × (1분×48h=2,880) ≈ 34.6만 행 ≈ 30MB hourly 120 × (1시간×30일=720) ≈ 8.6만 행 ≈ 8MB ───────────────────────────────────── 합 ~43만 행 ≈ 40MB (고정 · 자동삭제로 안 늘어남)

한 화면이 읽는 건 수백~천 행(인덱스로 그것만). 처음 DB 만들 때 과거 48h+30일을 결정적 함수로 미리 생성·적재(시드) → 그래프가 처음부터 차 있음. 슬라이스 수만 함대 규모에 따라 ±.

A ─< B = A 1 : N B (B가 A의 id를 FK로 가짐). 파랑=PK, 주황=FK.

3공유 도메인 (enum 대체)

union 타입(Status 등)은 Postgres DOMAIN + CHECK로. enum 타입보다 값 추가/변경이 쉬워 데모에 적합(ALTER TYPE 락 회피).

-- 여러 테이블이 공유하는 값 집합 → 도메인으로 한 번만 정의(DRY)
create domain status as text check (value in ('pending','approved','rejected'));
create domain server_health as text check (value in ('normal','warn','danger','inactive'));
create domain gpu_health as text check (value in ('normal','danger','inactive'));
create domain role as text check (value in ('admin','user'));
-- 그 외 인라인 CHECK: alloc_mode, severity, event_status, change_type, model_kind, capacity_unit ...
ID 전략: 시드가 의미있는 문자열 ID('u-admin', 'srv-01', 'gpu-a01')를 쓰므로 PK = text 유지(시드·기존 코드 호환). 런타임 신규 레코드는 앱에서 req-${crypto.randomUUID()} 생성. 배열(tags·addons·models·hosted_*)은 정규화 대신 text[](데모 단순성). 중첩(server>gpu>slice)만 정규화 테이블로 분리.

9시드 적재 — seed.json → DB (1회)

seed.json의 키 순서대로 FK 의존성 순서 INSERT. 멱등(idempotent)하게 on conflict do nothing.

  1. 스키마 SQL 적용 (도메인 → 엔티티 테이블 → 텔레메트리 테이블 → 인덱스). infra/db/init/0001_schema.sql
  2. 적재 순서: users → models → services → gpu_servers → gpus → mig_slices → (신청류) → event_logs → 나머지. (FK 부모 먼저)
  3. 적재 스크립트: Node infra/db/seed/seed-db.ts — seed.json 읽어 pg로 batch insert. servers.ts가 fleet 스펙→GpuServer[] 빌드하던 로직을 그대로 재사용해 gpus·slices 풀어서 INSERT.
  4. 검증: 적재 후 row count + 기존 verifyIntegrity를 DB판으로(끊긴 FK 0 확인).
텔레메트리는 별도 — 시드 시 과거 48시간(원본) + 30일(1시간평균)을 결정적 함수로 미리 생성·적재해야 그래프가 처음부터 차 있음(★ 섹션). 엔티티의 현재 temp·util 값은 latest 테이블 초기값으로.

10접근 레이어 — Hono backend + fetch 훅

화면이 동기 import { gpuRequests }에서 비동기 훅으로 전환. backend가 SQL을 감싼 REST를 주고, 프론트는 fetch. 공통 계약을 먼저 만들어 화면별로 분산.

// app/src/data/hooks/useGpuRequests.ts
export function useGpuRequests(status?: Status) {
  return useQuery(['gpu_requests', status], () =>
    fetch(`${API}/api/gpu-requests?status=${status ?? ''}`).then(r => r.json()))
}

11로컬 Docker 셋업 (지금) · 63번 배포 (나중)

지금 — 내 PC 로컬 (DB만 Docker)
